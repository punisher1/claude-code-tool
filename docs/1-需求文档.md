## 1 核心架构设计

### 1.1 数据源分层

Provider 的定义来源分为两层，优先级由高到低：

1.  **Custom (用户自定义)**: 存储在 `~/claude-code-tool/config.toml` 的 `[custom_providers]` 节点中。
2.  **Built-in (内置)**: 硬编码在程序源码中（未来可扩展为从远程 JSON 动态拉取）。**不持久化到本地文件。**

### 1.2 文件系统

  * **配置文件**: `~/claude-code-tool/config.toml`
      * 存储用户的 **API Key 实例** 和 **自定义 Provider 模板**。
  * **目标文件**: `~/.claude/settings.json`
      * `claudecode` 的原生配置文件，本工具负责修改其 `env` 字段。

## 2 数据结构 (TOML)

`config.toml` 将同时承载“自定义模板”和“配置实例”。

**结构示例**:

```toml
# 当前激活的实例别名
current = "my-work"

# [区域 1] 用户自定义的 Provider 模板
# 这里只存用户新增的，或者用户想覆盖内置定义的模板
[providers]

  [providers.ollama-local]
  description = "Local Ollama Llama3"
  [providers.ollama-local.env]
  ANTHROPIC_AUTH_TOKEN = "sk-xxxxxxxx"
  ANTHROPIC_BASE_URL = ""
  ANTHROPIC_MODEL = "kimi-k2-thinking"
  ANTHROPIC_DEFAULT_HAIKU_MODEL = "kimi-k2-thinking"
  ANTHROPIC_DEFAULT_SONNET_MODEL = "kimi-k2-thinking"
  ANTHROPIC_DEFAULT_OPUS_MODEL = "kimi-k2-thinking"

# [区域 2] 具体的账号配置实例
[configs]

  [configs.my-work]
  provider = "zhipu-glm"  # 引用内置 Provider
  description = ""
  [configs.my-work.env]
  ANTHROPIC_AUTH_TOKEN = "sk-xxxxxxxx"
  ANTHROPIC_BASE_URL = ""
  ANTHROPIC_MODEL = "kimi-k2-thinking"
  ANTHROPIC_DEFAULT_HAIKU_MODEL = "kimi-k2-thinking"
  ANTHROPIC_DEFAULT_SONNET_MODEL = "kimi-k2-thinking"
  ANTHROPIC_DEFAULT_OPUS_MODEL = "kimi-k2-thinking"
  HTTP_PROXY = ""
  HTTPS_PROXY = ""

  [configs.my-home]
  provider = "ollama-local" # 引用自定义 Provider
  description = ""
  [configs.my-home.env]
  ANTHROPIC_AUTH_TOKEN = "sk-xxxxxxxx"
  ANTHROPIC_BASE_URL = ""
  ANTHROPIC_MODEL = "kimi-k2-thinking" # 对应 ANTHROPIC_MODEL 
  ANTHROPIC_DEFAULT_HAIKU_MODEL = "kimi-k2-thinking" # 对应 ANTHROPIC_DEFAULT_HAIKU_MODEL 
  ANTHROPIC_DEFAULT_SONNET_MODEL = "kimi-k2-thinking" # 对应 ANTHROPIC_DEFAULT_SONNET_MODEL 
  ANTHROPIC_DEFAULT_OPUS_MODEL = "kimi-k2-thinking" # 对应 ANTHROPIC_DEFAULT_OPUS_MODEL
  HTTP_PROXY = ""
  HTTPS_PROXY = ""
```

## 3 Provider 加载逻辑 (Runtime)

程序运行时构建 Provider 列表的逻辑如下：

1.  **加载内置列表**:
    ```javascript
    const builtIns = {
      "claudecode": { ... },            // 官方订阅
      "claudecode-console": { ... },    // 官方API
      "kimi-k2": { ... },
      "deepseek": { ... },
      "zhipu-glm": { ... }
    };
    ```
2.  **加载自定义列表**: 读取 `config.toml` 中的 `providers`。
3.  **合并策略**:
      * 将 Custom 列表合并入 Built-in 列表。
      * **覆盖原则**: 如果 Custom 中定义的名称（如 `deepseek`）与 Built-in 重名，则使用 Custom 的定义。这允许用户在不升级工具的情况下，紧急修正某个内置 Provider 的 URL。

## 5 功能命令详解

### 5.1 `cct provider` 子命令组

  * **`cct provider list` (或 `ls`)**
      * **逻辑**: 输出 [Built-in] + [Custom] 的合并列表。
      * **标识**: 建议在输出中用标记（如 `[System]` vs `[Custom]`）区分来源。
  * **`cct provider add`**
      * **功能**: 添加/更新自定义模板。
      * **交互**: 输入 Name, URL, Models。
      * **动作**: 写入 `config.toml` 的 `[providers]` 节点。
  * **`cct provider rm [name]`**
      * **逻辑**:
          * 只能删除 `config.toml` 中的自定义 Provider。
          * 如果用户尝试删除内置 Provider，报错提示“Cannot delete built-in provider”。
          * 删除前检查是否有 `[configs]` 正在引用它。

### 5.2 `cct add` (添加实例)

  * **语法**: `cct add -p <provider_name> [api_key] [alias]`
  * **逻辑**:
    1.  在 **合并后的 Provider 列表** 中查找 `<provider_name>`。
    2.  如果找不到，提示错误。
    3.  写入 `config.toml` 的 `[configs]` 节点。

### 5.3 `cct use` (激活)

  * **逻辑**:
    1.  从 `config.toml` 读取实例。
    2.  获取其 `provider` 名称。
    3.  从 **合并后的 Provider 列表** 中解析出 URL 和 Model 映射。
    4.  更新 `~/.claude/settings.json`。

### 5.4 `cct update`

考虑到内置 Provider 不持久化，如果远端 URL 变了，用户要么升级工具，要么自己 `provider add` 一个同名的来覆盖。为了方便，可以增加一个检查更新机制（如果是做成自动从 GitHub 拉取 JSON 的话）。

  * *目前阶段*: 暂时不需要，依赖工具版本更新即可。

## 6 开发路径建议

1.  **数据层**: 编写 `ConfigManager` 类，负责 TOML 读写。
2.  **Provider 层**: 编写 `ProviderRegistry` 类，负责 `Built-in + Custom` 的合并逻辑。
3.  **CLI 层**: 实现各子命令。
