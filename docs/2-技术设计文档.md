# 技术设计文档 - claude-code-tool (Rust版)

## 1. 技术选型

### 1.1 核心语言
*   **语言**: Rust (Edition 2021)
*   **理由**: 高性能、内存安全、单一可执行文件分发方便、优秀的 CLI 生态。

### 1.2 关键依赖库
| 类别 | 库名称 | 版本建议 | 用途 |
| :--- | :--- | :--- | :--- |
| **CLI 解析** | `clap` | `4.x` (derive) | 命令行参数解析、子命令管理、帮助信息生成。 |
| **交互式 UI** | `dialoguer` | `0.11` | 处理用户输入、选择列表、确认提示（如 `provider add` 时的交互）。 |
| **序列化** | `serde` | `1.0` | 结构体序列化/反序列化 (derive)。 |
| **配置格式** | `toml` | `0.8` | 解析 `config.toml`。 |
| **JSON 处理** | `serde_json` | `1.0` | 解析和修改 `settings.json`。 |
| **系统路径** | `dirs` | `5.0` | 获取用户 Home 目录等跨平台路径。 |
| **错误处理** | `anyhow` | `1.0` | 应用层错误处理（便于向上传播错误）。 |
| **错误定义** | `thiserror` | `1.0` | 库/模块层自定义错误类型。 |
| **日志** | `env_logger` + `log` | `0.11` / `0.4` | 简单易用的日志输出，通过环境变量控制级别。 |
| **静态资源** | `lazy_static` 或 `once_cell` | - | 用于定义全局静态的内置 Provider 数据。 |
| **测试辅助** | `tempfile` | `3.10` | 用于单元测试中创建临时文件和目录。 |

## 2. 项目结构

采用标准的 Rust 二进制项目结构，并在 `src` 下进行模块化拆分。

```text
claude-code-tool/
├── Cargo.toml          # 项目依赖配置
├── src/
│   ├── main.rs         # 程序入口，负责 CLI 解析和错误处理顶层捕获
│   ├── lib.rs          # 库入口（可选，用于暴露模块给集成测试）
│   ├── models.rs       # 核心数据结构定义 (Provider, Config, Settings 等)
│   ├── config_manager.rs # 负责 config.toml 的加载、保存、路径管理
│   ├── provider_store.rs # 负责内置与自定义 Provider 的合并逻辑
│   ├── claude_adapter.rs # 负责与 ~/.claude/settings.json 的交互
│   ├── commands/       # 具体子命令实现逻辑
│   │   ├── mod.rs
│   │   ├── provider.rs # impl for `cct provider ...`
│   │   ├── config.rs   # impl for `cct add`
│   │   └── switch.rs   # impl for `cct use`
│   └── utils.rs        # 通用工具函数 (如路径展开)
└── tests/              # 集成测试
```

## 3. 模块划分与详细设计

### 3.1 数据模型 (`models.rs`)
定义所有核心结构体，并派生 `Serialize`, `Deserialize`, `Clone`, `Debug`。

*   `Provider`: 定义 Base URL, Models 映射。
*   `ConfigInstance`: 定义具体的账号配置（引用 Provider, Auth Token 等）。
*   `AppConfig`: 对应 `config.toml` 的根结构，包含 `providers` (Map), `configs` (Map), `current` (String)。
*   `ClaudeSettings`: 对应 `settings.json`，主要关注 `env` 字段。

### 3.2 配置管理器 (`config_manager.rs`)
*   **职责**:
    *   确定配置文件路径 (`~/.config/claude-code-tool/config.toml` 或 `~/claude-code-tool/config.toml`，根据需求文档定为后者)。
    *   `load()`: 读取并反序列化，若文件不存在则返回默认空配置。
    *   `save()`: 序列化并写入磁盘，原子写入（先写临时文件再 rename）以防损坏。

### 3.3 Provider 仓库 (`provider_store.rs`)
*   **职责**:
    *   维护 `BUILTIN_PROVIDERS` (使用 `lazy_static` 或 `const` 定义)。
    *   提供 `get_all_providers(custom_providers)` 方法，执行 Merge 逻辑：
        *   创建一个 HashMap。
        *   插入所有 Built-in。
        *   插入所有 Custom（同名覆盖）。
    *   提供 `get_provider(name)` 查询方法。

### 3.4 Claude 适配器 (`claude_adapter.rs`)
*   **职责**:
    *   定位 `~/.claude/settings.json`。
    *   `update_env(env_vars)`: 读取 JSON，修改 `env` 字段，保持其他字段不变，回写 JSON。
    *   **注意**: 必须处理 JSON 格式化，尽量保持原文件的缩进（`serde_json::to_string_pretty`）。

### 3.5 命令行交互 (`commands/`)
*   使用 `clap` 的 `Subcommand` 枚举定义命令结构。
*   **Provider Command**:
    *   `list`: 遍历合并后的 Provider 列表打印表格。
    *   `add`: 使用 `dialoguer` 提示用户输入各项参数，更新 AppConfig 并保存。
    *   `rm`: 检查是否为内置，检查是否被引用，从 AppConfig 删除并保存。
*   **Add Command**:
    *   接收参数，验证 Provider 是否存在，更新 AppConfig。
*   **Use Command**:
    *   根据 alias 找到 ConfigInstance。
    *   解析出完整的环境变量 Map。
    *   调用 `ClaudeAdapter` 更新设置。

## 4. 错误处理

使用 `anyhow::Result` 作为 `main` 和顶层 Command 函数的返回类型，以便于统一打印错误堆栈或友好信息。

*   **自定义错误 (`thiserror`)**: 在 `config_manager` 等底层模块定义明确的错误类型，如 `ConfigLoadError`, `ProviderNotFound`, `BuiltinDeleteError`。
*   **用户提示**: 在 CLI 层捕获错误，打印红色的 `Error: ...` 信息，而不是直接 Panic。

## 5. 单元测试策略

本项目采用 Rust 标准的 `cargo test` 框架。测试代码应放置在各模块源码文件的底部 `mod tests { ... }` 块中。

### 5.1 关键测试点

| 模块 | 测试内容 | 策略/工具 |
| :--- | :--- | :--- |
| **models** | 序列化/反序列化正确性 | 编写 TOML 和 JSON 字符串样例，验证 `from_str` 和 `to_string` 的结果。 |
| **config_manager** | 配置文件的加载与保存 | 使用 `tempfile` 创建临时目录，模拟配置文件不存在、存在但为空、存在且内容正确等场景。 |
| **provider_store** | 合并逻辑 | 验证自定义 Provider 是否正确覆盖内置 Provider；验证未覆盖时内置 Provider 是否保留。 |
| **claude_adapter** | JSON 局部更新 | 创建包含额外字段的模拟 `settings.json`，验证更新 `env` 后，其他字段（如 `theme`）是否完好无损。 |
| **commands/switch** | 环境变量生成逻辑 | 这是一个纯逻辑函数测试。给定 Config 和 Provider，验证生成的 HashMap 是否包含预期的 `ANTHROPIC_BASE_URL` 等键值。 |

### 5.2 Mocking 策略
由于项目逻辑主要依赖文件系统，推荐使用 **临时文件 (Temporary Files)** 而非复杂的 Mock 框架。
*   对于 `ConfigManager` 和 `ClaudeAdapter`，让它们的构造函数或方法接受一个 `PathBuf` 参数（而不仅仅是硬编码路径），这样测试时可以传入 `tempfile::NamedTempFile` 的路径。

## 6. 构建与部署

*   **构建**: `cargo build --release`
*   **二进制优化**: `strip` 二进制文件以减小体积。
*   **分发**:
    *   Windows: `cct.exe`
    *   Linux/macOS: `cct` (无后缀)
    *   未来可发布到 crates.io 或提供 GitHub Actions 自动构建 Release。

## 7. 日志

*   使用 `log` crate 埋点。
*   默认级别 `Info` 或 `Warn`。
*   用户可通过 `RUST_LOG=debug cct ...` 开启调试日志，方便排查配置加载问题。
